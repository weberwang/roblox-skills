# 决策与变更交接

产品、体验、架构、视觉、成本、隐私、风险或发布取舍无法由证据消除时，调用 [Roblox 游戏拷问](../../roblox-game-grilling/SKILL.md)。用户直接要求“拷问”同样进入该技能；这不是每个工作项都要经过的固定审批阶段。

## 触发之前

1. 读取当前工作项、GDD/TDD、视觉基线、实际源文件、Studio 已提供的只读状态及相关有效决策。先核对真实对象与范围，不重复问已有明确回答。
2. 能查明的 API、模式、对象位置、资产是否存在或日志事实，先通过只读工具解决；没有证据的内容明确标记假设或未知。
3. 首次实现、代码整理、小修和普通已授权验证都不单独触发。已有目标内的低风险可逆选择可记录假设后实施；继续确实需要用户作取舍时才暂停相应内容。

## 拷问与恢复

高影响或相互依赖问题一次只问一个，说明事实、实际影响、二至三个互斥选项与推荐理由。低影响且独立事项可以组合；用户可以自由回答，不强迫接受推荐项。回答含糊、与现有批准冲突或对象不明时澄清当前问题，不自行补成批准。

取得回答后展示具体结论：批准对象、范围、非目标、拒绝项、接受风险、验收和下一步。用户明确批准摘要后回交原工作项；同一真实用户消息已明确覆盖完整结论时可复用，不重复请求确认。

使用普通文件工具在 `.workflow-control/decisions/` 保存[决策记录](../../roblox-game-grilling/references/decision-record.md)，把路径加入当前 Work Item.decisionRefs。控制面 status/check 会核验文件、工作项/对象/修订、问题回答、结论与用户批准记录；pending、answered、rejected 或无效引用不能满足完成门。

未决时，冻结直接依赖该决定的实现、资源批产和状态推进；只读调查、候选比较和独立且已授权的工作继续。控制工具不执行 Studio 写入，因此编排者仍负责在生产动作前核对未决内容，不能等到最后 check 才发现越界。

## 变更与权限

- 范围内实现调整、普通候选变更、来源版本变化不自动撤销产品决定，也不计算 SHA。
- 用户实质改变目标、范围或撤回批准时，保留旧记录并明确受影响范围。修订增加后重新处理必要问题；旧记录标为 superseded 时必须指向同一对象更高修订、已批准且显式引用的替代记录。
- 拷问记录不能扩展文件/实例白名单，也不能代替已有的视觉人工确认或 operations 中的上传、付费、线上写入、真机和发布授权。
- 决策闭合后，在原任务已授权范围内恢复可逆文件或 Studio 实施；不再要求一轮重复实施批准。新范围或高影响外部操作另行核对真实授权。

本地 JSON 只是可审查记录，不证明用户身份或批准真实性。必须对照真实对话/宿主可信收据，不从代理审查、技术 PASS、文件作者、沉默或超时推定用户决定。
