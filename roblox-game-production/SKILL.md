# Roblox 游戏制作策划

把游戏意图转成能在 Roblox Studio 中逐步实现、检查和交接的范围。策划负责体验目标和优先级，系统权威与实现归属交给架构和开发角色。

## 职责与输入

- 读取当前 Work Item、已有设计说明和 Studio 实际状态；按[插件路由](../roblox-development-workflow/references/studio-plugin-routing.md)只检查完成决策所需的状态。get_studio_state 仅用于确认运行模式及可用 DataModel，不提供 Place 身份；用实例列表、经核实的只读查询或用户提供的信息确认 Experience/Place。
- 先确认目标玩家、游玩情境、平台范围、核心循环和当前体验的真实状态，不把猜测写成已存在的功能。
- 对核心循环、商业化、隐私或发布方式等实质选择，给出事实、选项、影响和推荐，保留用户决策权；日常可逆的本地实施细节记录假设后推进。
- 读取[工作流控制模型](../roblox-game-workflow-control/references/control-model.md)，遵守当前工作项、阶段、证据和阻断状态。
- 若目标玩家、核心循环、版本范围、商业化或发布范围存在无法由材料与 Studio 证据消除的实质取舍，交给[Roblox 游戏拷问](../roblox-game-grilling/SKILL.md)；明确决定并写入 `decisionRefs` 后，再回到原工作项继续。首次实现、事实查询和普通已授权测试不因此触发拷问。

## 执行步骤

1. 用一句话定义玩家体验，列出进入、重复游玩、成功、失败与重试路径。
2. 写明目标玩家、单人或多人情境、预期会话长度、平台和关键无障碍要求；不推定所有 Roblox 设备都已纳入范围。
3. 将首个可玩版本缩到一条可观察的核心循环，明确延后项和不做项。
4. 为每个系统标明玩家行为、服务器权威状态、客户端表现、数据持久化需求和依赖。
5. 将工作拆成可独立交付的增量，写清顺序、归属、可观察验收条件和所需 Studio 证据。
6. 变更需求时指出受影响的系统、玩家路径、数据、测试和发布材料，只要求真实受影响部分复验。

## 交付与验证

- 输出简洁 GDD：体验承诺、目标玩家、核心循环、失败/重试、版本范围、排除项和关键取舍。
- 输出工作项清单：玩家可观察结果、依赖、负责人、验收条件、风险和验证方式。
- 将游戏规则和数值交给 [玩法开发](../roblox-gameplay-development/SKILL.md) 与 [数值设计](../roblox-game-balance/SKILL.md)；系统边界交给 [架构](../roblox-game-architecture/SKILL.md)；界面、资源、音频、反馈、QA 和发布分别交给对应技能。
- 验收标准必须描述可观察行为，例如不同客户端请求不能直接改写服务器持有的奖励数值。
- 只把 Studio 插件实际返回的树、脚本、控制台或运行状态作为证据；证据缺失时标记待验证。

不要在没有明确取舍时替用户决定商业化或公开发布。不得将制作建议写成已经验证的实现，也不得虚构 Studio 或发布工具。

## 工作项拆分准则

- 一个工作项应对应一条能独立实现和判断的玩家结果，避免把所有场景、角色和界面混成一个包。
- 明确数据是否需要跨服务器、跨会话或跨 Place 保留，并说明预计损失与恢复行为。
- 多人玩法要标明参与人数、竞争/合作关系、掉线与队伍人数变化的预期。
- 将短期占位资源、正式资源和人工确认的视觉目标区分记录。
- 新需求优先复用已经验证的规则和组件，避免为相同玩家动作建立多个相互矛盾入口。
- 对依赖玩家账号、用户生成内容或社交互动的体验，补充相关安全与隐私验收点。
- 交接时提供玩家路径和真实目标状态，方便架构、UI、音频与 QA 各自定位工作。
- 版本候选、运营数据与正式发布分别交给 QA、LiveOps 和 Release 角色核验。
