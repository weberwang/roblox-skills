# 控制模型

## 与 Unity 工作流的对应

保留控制面、领域编排、插件执行的职责分离，以及“需求范围 → 全局基线 → 基础工程 → 场景与显示层生产 → 全局集成验证 → 发布”六阶段。范围/所有权、实施包、F0–F4、证据绑定、repair/revalidate/return 继续适用。

不复制 Unity 的 GUID、`.meta`、AssetDatabase、URP、Prefab、程序集和域重载语义。Roblox 使用 Studio 实例、Place/Universe、DataModel、Instance 路径、Asset ID、Script/LocalScript/ModuleScript、服务器权威和复制边界。

## V0–V4 交付

| 步骤 | 实际交付 | 执行约束 |
| --- | --- | --- |
| V0 分流 | 场景/显示层身份、目标、宿主、资源与依赖 | 已有范围可直接复用，不重复问已知问题 |
| V1 定义 | 玩法轨迹、状态、布局意图、目标设备与必要效果图 | 新方向存在实质选择时展示候选 |
| V2 拆解 | 实例树、脚本职责、资源来源、事件与布局接口 | 先复用现有组件，不用整张效果图替代可交互 UI |
| V3 组合 | 实际资源和 Edit 模式实例组合、引用回读 | 视觉结果交用户检查，不自动分析截图 |
| V4 接入 | 真实交互、重生/退出清理、Console、运行证据 | 技术结果与人工视觉确认分别保存 |

场景/显示层独立工作项；宿主场景不能代替弹窗验收。只为本次涉及对象维护记录，避免把所有领域都变成必经门。

## 操作风险

| 级别 | Roblox 语义 | 处理 |
| --- | --- | --- |
| A0 | 读实例/脚本/日志/官方文档 | 绑定目标，最小必要查询 |
| A1 | 规格、工作项、实施包 | 本地可逆写入按任务推进 |
| A2 | 隔离原型 | 明确路径与清理边界 |
| A3 | Edit 模式正式实例与脚本实现 | 先读后改，单写者，写后回读 |
| A4 | 本地跨系统集成 | 核对影响范围，普通本地验证自动执行 |
| A5 | 上传、外部配置、真实设备 | 需要对应对象和影响的明确授权 |
| A6 | 公开发布、付费、线上迁移/破坏性操作 | 完成本地候选后核对或请求精确授权 |

生成资源是否插入场景、是否上传、是否付费，以实际工具说明为准，不能将所有生成视为纯本地操作。明确授权过的同一对象不重复询问。

## F0–F4

- F0：任务、目标 Studio/Place、源数据、文件/实例范围及停止条件明确。
- F0 中的必要用户取舍统一交给[拷问技能](../../roblox-game-grilling/SKILL.md)，通过 decisionRefs 保留真实回答、摘要批准与修订；没有取舍时保持空数组，不能把普通实施变成审批流程。
- F1：交付行为符合用户目标；范围内实现调整记录事实，不要求为验收回改规格。
- F2：客户端/服务端、安全、生命周期、资源、UI、玩法和适用领域质量通过。
- F3：静态、回读、Console、Play、多人、性能证据按实际影响覆盖，失败修复并复验。
- F4：外部/高影响动作具有真实、当前、精确的用户授权及操作结果。

`check` 验证版本 2 记录结构、实施依赖和所有权、逐条验收与验证覆盖、工作项/候选/Studio/Place/Universe 证据身份、可见合同及阶段交付。它不证明日志内容真实，也不能核实消息引用确实来自用户。编排者必须对照真实工具输出与对话；不能把 `ready=true` 写成“引擎验收通过”。具体字段以[记录契约](record-contract.md)为准。

同一 Studio 正式写入串行。源数据是 Studio 时，不凭空安装 Rojo；源数据是文件时，先确认已有同步映射与进程，避免在 Studio 修改后被文件同步覆盖。

完整项目的[工作项依赖](project-contract.md)与单包实施单元依赖分开：前者绑定上游候选及完成门，`check-project` 聚合全部工作项和最终集成项；后者安排包内所有权和执行顺序。[覆盖门](coverage-contract.md)验证批准用例的运行证据，[资源门](asset-bindings.md)验证当前消费者的许可、修订及实际回读。多 Place 仅由项目清单显式开启，仍须逐目标核实 Studio 工具能力和外部授权。
